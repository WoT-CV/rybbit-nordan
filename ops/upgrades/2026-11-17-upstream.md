kanoniczne, bez symlinków. Dokładne hashe/polecenie powstają po finalnym

```text
sudo python3 -B -I <root-private-packet>/wotcv-native-release.py \
  --manifest <root-private-packet>/manifest.json \
  --manifest-sha256 <reviewed-manifest-sha256> \
```

Operator korzysta z działającej sesji z interaktywnym sudo. Alias audytowy

`( set -e; ... )`, aby błąd nie zamknął sesji operatora. Nie używać `set -x`.

## Rollback i obsługa awarii

Niepowodzenie capture prowadzi do bezpiecznej próby wznowienia poprzednich
aplikacji. Drift DB pozostawia writery zatrzymane do inspekcji. Brak PASS
restore blokuje build/aktywację. Nierozpoznany błąd zatrzymuje proces;
pending pozostaje i nie wolno go kasować dla ponowienia.

Native apply ma własny rollback obrazów po awarii aktywacji. Orchestrator
dodatkowo zatrzymuje rozpoznane writery kandydata po błędzie późniejszej
kontroli lub przerwaniu aktywacji. Weryfikuje końcowy stan także przy
`restarting`; nie deklaruje zatrzymania bez ponownego inspect.

Powrót po negatywnej akceptacji funkcjonalnej korzysta z tej samej
przejrzanej paczki i osobnego ACK:

```text
sudo python3 -B -I <root-private-packet>/wotcv-native-release.py \
  --manifest <root-private-packet>/manifest.json \
  --manifest-sha256 <reviewed-manifest-sha256> \
  --rollback-operation <original-operation-id> \
  --ack rollback-native-reviewed-release
```

Rollback dopuszcza wyłącznie nadal aktywne wydanie powiązane z tą operacją,
zgodne DB/journal i dokładne stare obrazy oraz env. Tworzy nową transakcję
i prawdziwy receipt zamiast przepisywania historii. Przywraca aplikację
i konfigurację bez utraty późniejszych zapisów. Nie buduje, nie wykonuje
migracji, nie odtwarza danych i nie wraca automatycznie do wadliwego wydania.

Zmiana journal/schematu albo uszkodzenie danych oznacza HOLD i osobny plan
recovery z zatrzymaniem writerów. Zachowane PG dump/globals, CH archive,
Redis RDB, env/config i hashe stanowią punkt odzyskania. Produkcyjny restore
wymaga wskazania celów, akceptacji overwrite/utraty zapisów po capture oraz
sprawdzenia ról/ACL i auth w nowym celu. Ten pakiet nigdy nie odtwarza baz
produkcyjnych automatycznie.

Ograniczenia drillu są jawne: PG ownership/ACL/globals nie są replayowane,
CH backup bazy nie obejmuje access management, nie sprawdzono całej aplikacji
przeciw odtworzonym bazom, a lokalna kopia nie zabezpiecza utraty hosta.
Nie przedstawiać tego jako pełny disaster recovery ani pomiar RPO/RTO.

## Akceptacja działającego wydania

Niezależnie powiązać published SHA → image revision/ID → rzeczywisty
kontener → ruch przez proxy. Sprawdzić nowe logi bez ujawniania sekretów,
stabilne restarty i dane sprzed aktualizacji. Oznaczyć każdy scenariusz
PASS/FAIL/NOT_VERIFIED z czasem i dowodem:

| Scenariusz | Wymagana obserwacja |
| --- | --- |
| Public config/login | Self-hosted, signup disabled, właściwe SHA i origin, brak regresji hydratacji |
| Tracker | script/replay/metrics, gzip/Brotli po dekompresji zgodne, prawidłowe cache/encoding |
| Site po auth | Rzeczywista sesja, dotychczasowe dane, zmiana zakresu czasu i filtrów, poprawne API |
| Replay WoT-CV | Istniejące nagranie, odtwarzanie i panel requestów z właściwym czasem/polami |
| Loki/Tempo | Właściwy profil/service/env/datasource, correlation/trace ID i dostępne dane |
| Zmiany upstream | Eksport eventów i kontrola uprawnień admin API keys, adekwatnie do sesji |
| Ingestion | Dozwolony test na dedykowanej Site lub odczyt faktycznego ruchu bez sztucznych zapisów |

Health, login, build i techniczny receipt nie zastępują tej akceptacji.
Brak sesji lub danych oznacza konkretną lukę, nie PASS. Końcowy raport musi
rozdzielać przygotowane, przetestowane, zacommitowane, opublikowane,
wdrożone i potwierdzone na serwerze.
