potwierdza gotowości wydania i nie jest nowym mechanizmem wdrożeniowym. Nie

## 1. Odczytowy preflight operatora

Polecenia poniżej są przeznaczone dla operatora z legalnym, interaktywnym sudo.
Nie zastępują tego dostępu. Wykonywać na właściwym hoście po `ssh wotcv-audit`;
brak sudo oznacza zakończenie kroków wymagających uprawnień. Nie kopiować env,
pełnego `docker inspect`, pełnego Compose configu, globals SQL ani prywatnych
logów do raportów. Nie używać `set -x`.

```bash
set -euo pipefail
umask 077
sudo -v
project=rybbit-wotcv-native
native_docker() { sudo /usr/bin/docker --host unix:///var/run/docker.sock "$@"; }
evidence=$(mktemp -d /var/tmp/rybbit-upgrade-20261117.XXXXXXXX)
date -u +%FT%TZ > "$evidence/observed-at.txt"
docker compose version --short
sudo sha256sum /usr/local/lib/wotcv-rybbit-native/update.py
native_docker ps -a --filter "label=com.docker.compose.project=$project" \
  --format '{{.ID}} {{.Label "com.docker.compose.service"}} {{.State}}'

service_id() {
  local result
  result=$(native_docker ps -aq \
    --filter "label=com.docker.compose.project=$project" \
    --filter "label=com.docker.compose.service=$1")
  if test -z "$result" || test "$(printf '%s\n' "$result" | wc -l)" -ne 1; then
    printf '%s\n' 'HOLD: niejednoznaczna identyfikacja usługi' >&2
    return 1
  fi
  printf '%s\n' "$result"
}
backend=$(service_id backend)
client=$(service_id client)
pg=$(service_id postgres)
ch=$(service_id clickhouse)
redis=$(service_id redis)
for cid in "$backend" "$client" "$pg" "$ch" "$redis"; do
  native_docker inspect --format \
    '{{.Id}} {{.Image}} {{.State.Status}} {{if .State.Health}}{{.State.Health.Status}}{{end}} {{.RestartCount}} {{.State.StartedAt}}' \
    "$cid"
done | tee "$evidence/runtime-before.txt"
for cid in "$backend" "$client"; do
  image=$(native_docker inspect --format '{{.Image}}' "$cid")
  native_docker image inspect --format \
    '{{.Id}} {{index .Config.Labels "org.opencontainers.image.revision"}}' "$image"
done | tee "$evidence/revisions-before.txt"
for cid in "$pg" "$ch" "$redis"; do
  native_docker inspect --format \
    '{{.Id}}{{range .Mounts}} {{.Type}}:{{.Name}}:{{.Destination}}:rw={{.RW}}{{end}}' "$cid"
done | tee "$evidence/storage-before.txt"
curl --fail --silent --show-error --max-time 15 \
  https://tracking.wot-cv.com/api/config |
  python3 -c 'import json,sys; c=json.load(sys.stdin); print(json.dumps({k:c.get(k) for k in ("sourceCodeUrl","disableSignup")},sort_keys=True))' |
  tee "$evidence/public-config-before.json"
curl --fail --silent --show-error --max-time 15 \
  http://127.0.0.1:13001/api/health
```

Wymagane: dokładnie pięć oczekiwanych usług, właściwe image IDs i rewizje,
brak restartów wskazujących awarię, zdrowe bazy/backend, `disableSignup=true`,
Compose co najmniej `2.24.4`, zachowane dedykowane wolumeny i brak obcego
consumera tych wolumenów. Operator dodatkowo sprawdza ownership, network, porty,
receipt i zgodność effective env z runtime zgodnie z `snapshot()`, `model_guard()`,
`verify_model_live()` oraz `receipt_guard()` istniejącego updatera. Nie wystarczy
porównać nazw usług ani zmiennych z checkoutu.

Odczyt wersji i applied journal nie wypisuje danych kont ani sekretów. Zmienne
połączenia są używane wewnątrz kontenera, bez wyświetlania ich wartości:

```bash
native_docker exec "$pg" sh -ec '
  export PGPASSWORD="$POSTGRES_PASSWORD"
  exec psql -X -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Atc \
    "SELECT version(); SELECT created_at, hash FROM drizzle.__drizzle_migrations ORDER BY created_at, id;"
' > "$evidence/postgres-version-journal.txt"
native_docker exec "$ch" clickhouse-client --query 'SELECT version() FORMAT TSV' \
  > "$evidence/clickhouse-version.txt"
```

Jeżeli tabela journalu nie istnieje, uprawnienia nie wystarczają albo odczyt
zawiedzie, zatrzymać procedurę i ustalić rzeczywistą konfigurację migratora.
Brak wyniku nie oznacza braku zaległych migracji. Zweryfikować wszystkie
`created_at/hash` wobec plików SQL i `_journal.json` rewizji live, a następnie
rewizji kandydata; nie porównywać samych nazw lub liczby migracji.

W repozytorium ostatecznego wydania, po ustawieniu `RELEASE_SHA` na konkretny
przejrzany commit, wykonać ponowne porównanie. Pusty wynik jest warunkiem
rozważenia wariantu bez migracji, nie zgodą na wdrożenie:

```bash
: "${RELEASE_SHA:?Ustaw dokładny przejrzany SHA wydania}"
git cat-file -e "$RELEASE_SHA^{commit}"
git diff --exit-code c7b638b5af2249d420de7a46b946477e0eb3b67f "$RELEASE_SHA" -- \
  package.json pnpm-lock.yaml pnpm-workspace.yaml shared/package.json \
  client/package.json server/package.json client/Dockerfile server/Dockerfile \
  server/docker-entrypoint.sh server/drizzle server/drizzle.config.ts \
  server/src/db server/src/cluster.ts docker-compose.yml ops/minimal
```

Przejrzeć również pełny diff backendu i ścieżek inicjalizacji. Backend startuje
Drizzle z `server/docker-entrypoint.sh`, a następnie inicjalizuje PostgreSQL oraz
ClickHouse z kodu. Brak zmian plików SQL nie wyklucza DDL wykonywanego w kodzie.

## 2. Backup oraz dowód odtwarzalności przed zmianą

Poniższe skrypty są dostępne w repozytorium; ich instalacja i konfiguracja na
tym hoście nie zostały potwierdzone. Operator najpierw sprawdza prywatnie:

- czy zainstalowane `backup-postgres.sh`, `backup-clickhouse.sh` i `common.sh`
  odpowiadają przejrzanym źródłom w `ops/backups/bin/`;
- czy konfiguracja wskazuje dokładnie powyższe kontenery i bazy native,
  a nie domyślne nazwy `postgres`/`clickhouse` lub inne środowisko;
- czy wybrany tryb ClickHouse ma działającą named collection S3 albo backup disk
  z dostępnym miejscem i poprawnym mountem; fresh overlay sam tego nie zapewnia;
- czy destination, retention, miejsce, czas i obciążenie backupu są właściwe;
  nie włączać przy tej operacji kasowania/prune;
- czy systemd services wskazują te same przejrzane skrypty i plik konfiguracji.

Odczyt metadanych instalacji i jobów, bez treści sekretów:

```bash
sudo sha256sum /opt/rybbit-backups/bin/backup-postgres.sh \
  /opt/rybbit-backups/bin/backup-clickhouse.sh /opt/rybbit-backups/bin/common.sh
sudo stat -c '%a %U:%G %n' /etc/rybbit-backup.env
sudo systemctl show rybbit-postgres-backup.service rybbit-clickhouse-backup.service \
  -p Id -p ActiveState -p Result -p ExecMainStatus -p ExecMainStartTimestamp \
  -p ExecMainExitTimestamp
```

Dopiero po potwierdzeniu instalacji, konfiguracji i celu operator może uruchomić
istniejące joby backupowe. Poniższe polecenia tworzą backup i mogą wysłać upload
oraz skonfigurowaną notyfikację; są krokiem zmieniającym stan, nie preflight:

```bash
sudo systemctl start rybbit-postgres-backup.service
sudo systemctl start rybbit-clickhouse-backup.service
sudo systemctl show rybbit-postgres-backup.service rybbit-clickhouse-backup.service \
  -p Id -p ActiveState -p Result -p ExecMainStatus -p ExecMainStartTimestamp \
  -p ExecMainExitTimestamp
```

Nie uruchamiać ich, jeśli unit/config dotyczy innego środowiska. `DRY_RUN=true`
istniejących skryptów zatrzymuje capture/upload, ale ich EXIT trap może wysłać
skonfigurowaną notyfikację. Nie jest to dowód działania backupu ani tryb całkowicie
pozbawiony efektów zewnętrznych. Konfiguracja jest sourcowana przez Bash;
zmienna przekazana przez `env` może zostać nadpisana jej treścią.

Zanotować oddzielnie identyfikator artefaktu PostgreSQL i ClickHouse, źródłowe
wersje i image IDs, zakres, początek/koniec, kod zakończenia, rozmiar i docelowy
obiekt. PostgreSQL obejmuje custom archive oraz globals; globals zawierają dane
wrażliwe i pozostają prywatne. ClickHouse backup obejmuje `analytics`, nie
regenerowalne logi `system`. Skrypty nie tworzą backupu Redis. Ustalić, czy Redis
ma stan potrzebny do przywrócenia spójności aplikacji; wykluczenie musi mieć
uzasadnienie. Nie zastępować backupu kopią aktywnego Docker volume.

Po pobraniu wybranego artefaktu PostgreSQL do prywatnego katalogu można
sprawdzić integralność bez wypisywania danych:

```bash
: "${PG_ARTIFACT_DIR:?Ustaw prywatny katalog pobranego artefaktu}"
test -f "$PG_ARTIFACT_DIR/SHA256SUMS"
(cd "$PG_ARTIFACT_DIR" && sha256sum --check SHA256SUMS)
native_docker exec -i "$pg" pg_restore --list \
  < "$PG_ARTIFACT_DIR/database.dump" > /dev/null
```

To potwierdza checksum/parsowanie, nie restore. Wymagany oddzielny drill:
disposable instancje zgodnych wersji, odrębne wolumeny/network, bez production
env i bez ruchu zewnętrznego. Odtworzyć oba wybrane artefakty; zachować operację
RESTORE ClickHouse i wynik terminalny, sprawdzić schemat, journal, constraints,
próbki/counts związane z punktem capture oraz odczyty aplikacji. Na tej kopii
przeprowadzić próbę uruchomienia kandydata i powrotu do starych obrazów. Dla
zmian schematu wymagany jest również test odtworzenia poprzedniego stanu danych.
Nie wykonywać próbnego restore na produkcji ani na współdzielonym PostgreSQL
z bezwarunkowym zastosowaniem globals.

Backupy obu silników wykonane przy aktywnych writerach nie gwarantują wspólnego
punktu transakcyjnego. Przed zmianą ustalić i przetestować sposób zatrzymania
writerów/flush danych oraz obsługę ruchu w oknie. Bez tego RPO i zgodność
międzybazowa pozostają niezmierzone. Udany upload, `rclone check`, `pg_restore
--list` oraz `health=OK` nie zastępują powyższego drillu.

## 3. Warunki zdjęcia HOLD i kolejność właściwego wdrożenia

Przed wykonaniem jakiegokolwiek przełączenia potrzebne są wszystkie elementy:

1. Ostateczny commit integracji, review pełnego diffu, publikacja konkretnego
   SHA i dowód przejścia testów/typecheck/build. Obrazy muszą pochodzić z tego
   SHA; `NEXT_PUBLIC_*` ustawia się podczas builda klienta. Zachować istniejący
   auth secret, correlation profile, publiczny origin i wyłączony signup.
2. Przejrzany mechanizm wydania kodu z testami. Musi obsługiwać istniejące
   receipts/private env, blokadę współdzielonych operacji, dokładny runtime
   snapshot, stare i nowe image IDs, source/env hashes, osobne stany
   preflight/backup/writers-stopped/activating/verified/failed oraz bezpieczne
   zatrzymanie po błędzie. Nie może podmieniać zapieczętowanego bootstrapu ani
   akceptować obcych wolumenów. Przygotowane `prepare/check/apply` obsługują
   dokładny kontrakt kodu; nie dopuszczają aktualizacji schematu ani zależności.
   Backup, journal i restore drill są warunkami operatora, a nie dowodem
   wynikającym z przejścia testów offline.
3. Applied journal i rzeczywisty schemat zgodne z rewizją live; dowód, że
   kandydat nie wprowadza migracji, DDL ani nowego zachowania inicjalizacji.
   Jeśli wynik się zmieni, przygotować osobny plan migracji i restore.
4. Zweryfikowane backupy i isolated restore/upgrade/rollback drill z wpisanym
   czasem, zakresem, ograniczeniami i recovery point. Sam kod backupu nie jest
   dowodem dostępności artefaktu.
5. Konkretne okno, sposób przyjmowania/wstrzymania ingestion, operator z sudo,
   kryteria przerwania i przetestowany rollback. Zachowane stare obrazy oraz
   prywatne previous env/receipts; nie uruchamiać Docker prune.

Po spełnieniu warunków operator wykonuje wyłącznie polecenia zatwierdzonego
mechanizmu: blokada i preflight, finalny punkt odtworzenia, zatrzymanie starych
writerów zgodnie z planem, aktywacja zgodnych obrazów backend/client z
zachowaniem kontenerów baz i wolumenów, walidacja oraz zapis receipt. Ten
dokument nie podaje `compose up` ani komendy omijającej source guard.

Po potwierdzeniu powyższych warunków oraz publikacji końcowego SHA interfejs
przygotowanego narzędzia ma następującą postać. Operator korzysta z prywatnej,
root-owned kopii przejrzanego narzędzia i sprawdza jej sumę przed wykonaniem;
przygotowanie może wykonać konto właściciela repozytorium. Zmienne wskazują
konkretne pliki/pakiet tego przebiegu, nie instalowany updater frontend-only:

```bash
: "${RELEASE_TOOL:?Zweryfikowany plik nowego updatera}"
: "${RELEASE_SHA:?Dokładny opublikowany SHA}"
: "${CODE_CONTRACT:?Plik przejrzanego kontraktu}"
CONTRACT_HASH=8075a5b1de902d0f940c9bfe10f63b6690713abd1d68d3382f08a9d1e731f2be
python3 -B -I "$RELEASE_TOOL" prepare --expected-sha "$RELEASE_SHA" \
  --code-contract "$CODE_CONTRACT" --code-contract-sha256 "$CONTRACT_HASH"
# Po otrzymaniu PREPARED ustawić dokładną ścieżkę pakietu:
: "${PREPARED_BUNDLE:?Dokładna ścieżka z wyniku prepare}"
python3 -B -I "$RELEASE_TOOL" check --bundle "$PREPARED_BUNDLE" \
  --code-contract-sha256 "$CONTRACT_HASH"
# APPLY dopiero po backup/restore/journal preflight i zamknięciu review:
sudo python3 -B -I "$RELEASE_TOOL" apply --bundle "$PREPARED_BUNDLE" \
  --ack update-native-apps-preserve-data --code-contract-sha256 "$CONTRACT_HASH"
```

`prepare` buduje obrazy i zapisuje prywatny pakiet bez startowania aplikacji.
`check` nie dowodzi backupu ani rzeczywistego schematu. `apply` zapisuje receipts,
używa wspólnej blokady i zmienia wyłącznie oba obrazy aplikacji oraz provenance.
Kontrakt przypina dotychczasowe image IDs i rewizję; po skutecznej aktywacji
nie można użyć go ponownie. Kolejne wydanie wymaga nowego przejrzanego kontraktu.
Nie podmieniono automatycznie zainstalowanego wrappera frontend-only.

## 4. Akceptacja po aktywacji

Powtórzyć odczytowy runtime snapshot z punktu 1. Porównać nowe image IDs i
etykiety ze zbudowanym release, publiczny `sourceCodeUrl` z konkretnym SHA,
a ID/StartedAt/mounty baz z `runtime-before.txt` i `storage-before.txt`.
Zweryfikować zero nieplanowanych restartów oraz brak błędów inicjalizacji.
Potwierdzić applied journal; przy wariancie bez migracji nie może się zmienić.

```bash
curl --fail --silent --show-error --max-time 15 \
  http://127.0.0.1:13001/api/health
curl --fail --silent --show-error --max-time 15 \
  https://tracking.wot-cv.com/login > /dev/null
for asset in script.js replay.js metrics.js; do
  curl --fail --silent --show-error --max-time 15 \
    "https://tracking.wot-cv.com/api/$asset" > "$evidence/$asset"
  test "$(wc -c < "$evidence/$asset")" -gt 1000
done
```

Operator z uprawnieniami w aplikacji sprawdza istniejącą sesję, ponowne
uwierzytelnienie i API key, historię/zakres danych, jeden dozwolony test
ingestion, replay oraz correlation z linkami do Grafany. Dla tej integracji
sprawdza również eksport eventów i nowe operacje admin API keys, ich kontrolę
uprawnień oraz odczyt danych dotychczasowego Site. Sekrety i dane kont nie
trafiają do raportu. Zewnętrzna strona logowania nie dowodzi poprawności auth,
a dostępny asset nie dowodzi przyjęcia eventu. Dopiero po pełnej akceptacji
zapisać verified receipt i przywrócić normalny ruch zgodnie z planem.

## 5. Wycofanie i warunki wymagające restore danych

**Wariant zgodnego schematu — rollback samych obrazów:** dopuszczalny wyłącznie,
gdy przed wdrożeniem wykazano identyczność zależności/DDL/inicjalizacji względem
live, applied journal był zgodny i nie zmienił się, a isolated drill potwierdził
powrót. Przy awarii zatrzymać nowe workery, zachować logi i failed receipt,
sprawdzić journal oraz schemat, następnie przetestowanym mechanizmem przywrócić
oba stare image IDs z tabeli i dokładny previous env. Zachować te same bazy,
ich kontenery/wolumeny i auth secret. Powtórzyć pełną akceptację, w tym
stare source label/public config, sesje, dane i ingestion. Samo przywrócenie
image ID nie jest dowodem zakończonego rollbacku. Błędy pozostawiają pending
marker; nie usuwać go w celu ponowienia.

**Niezgodny/nieznany schemat lub zmieniony journal:** wstrzymać nowe workery i
ruch zapisujący; nie uruchamiać starego backendu przeciw niepotwierdzonemu
schematowi i nie odpalać kolejnych migracji próbnie. Zachować evidence oraz
stan po błędzie. Ustalić, która operacja zmieniła dane, i wykonać osobno
zatwierdzony plan restore obu silników do zweryfikowanego recovery point,
z jawną oceną utraty zapisów po capture i spójności Redis. Produkcyjny restore
wymaga określonego celu, overwrite i procedury powrotu. Ten dokument nie zawiera
komendy odtwarzającej produkcję, ponieważ artefakty, cel i drill są obecnie
niezweryfikowane.

Jeśli wykryta rozbieżność obejmie migrację Better Auth 1.7.3, zastosować także
`server/docs/better-auth-1.7.3.md`: preflight otwierającego bloku DO migracji
0018, brak równoległych starych workerów podczas kopiowania, zgodny klient i
serwer. Powrót do starego auth może ponownie uaktywnić legacy tokeny; nowe
rejestracje/consent nie są kopiowane z powrotem. Nie traktować obecnej integracji
jako autoryzacji do nieplanowanej migracji auth.
